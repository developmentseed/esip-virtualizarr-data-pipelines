Data Pipelines

A template repository for building and operating Virtualizarr / Icechunk stores on AWS - You bring your data expertise and we bring the infrastructure.

developmentseed/virtualizarr-data-pipelines

Virtualizarr and Icechunk have largely solved the format problem — how to expose an archive of NetCDF, HDF5 or GRIB files as a single analysis-ready virtual dataset. What has not been solved is the operational problem: everything you have to build and run to keep a store current. This talk is about the second half. We will cover why we built the template, what it actually gives you, how the backfill works, where it is running, and what it takes to adopt it.

Why we built it

Bring the dataset knowledge, not the infrastructure

◆Your dataset knowledge

  • How to parse this particular format.
  • How these files concatenate into a cube and along which dimension.
  • What the coordinate axis means, and which variables don't carry it.
  • Which files are appends, which are in-place region writes.
+

⚙Repeatable infrastructure

  • Containerized Lambdas, a queue and its batching configuration.
  • Step Function orchestration, retries, concurrency limits.
  • Icechunk garbage collection on a schedule.
  • CDK code to configure and and deploy all the infrastructure
The premise. The second column is repeatable so it should be written once, tested once, and deployed the same way for every dataset. Teams should leverage their expertise to focus on how to parse and concatenate archival files without having to think too much about building infrastructure code.
Here is the division of labor the project is built around. The scarce expertise is dataset-specific: how to parse this format, how these files concatenate, what the coordinate axis means, which variables are static and have to be dropped for a region write. That is the part only the data owner can write, and it is genuinely hard. Everything in the right-hand column is the same for every dataset — containerized Lambdas, a queue and its batch size, orchestration, garbage collection, buckets and IAM. Today every team building an Icechunk store re-derives that column from scratch, and re-derives its failure modes along with it. Our premise is simply that the right-hand column is repeatable infrastructure. Write it once, test it, and let people deploy it identically for each new dataset. The README line is the thesis: leverage your expertise to focus on parsing and concatenating, without having to think too much about building infrastructure code.

What it is

A template repository, not a framework

1Start from a template

A GitHub template repository. You create your own repo from it with the naming convention: datasetname-virtualizarr-data-pipelines and it is yours to modify. No dependency to track, no upstream to fight.

2Implement one protocol

Write a processor.py satisfying the VirtualizarrProcessor protocol. A sample processor with an in-memory store ships in the repo as a working example.

3Configure with types

A strongly-typed settings module with sensible defaults, overridden by a .env file. Buckets, regions, topics, batch sizes, concurrency.

4Deploy with CDK

The infrastructure builds your Docker images and stands up the Lambdas, the Batch job, the queue and the Step Functions orchestration. cdk deploy.

5Two processing paths

Backfill for the historical archive, forward processing for new files as they land. Same processor, same deployment.

→The shape stays fixed

Every dataset gets the same deployment shape. What differs between projects is the processor and the configuration.

Deliberately a template repository rather than a library or a framework. You create your own repo from it and the code is yours — there is no upstream dependency to track and nothing stopping you from changing infrastructure you need to change. What you write is one processor module satisfying the VirtualizarrProcessor protocol; a sample processor using an in-memory store and a fake virtual dataset ships in the repo so you have a working reference. Configuration is a strongly-typed settings module with defaults you override in a dot-env file. The CDK then takes your processor, builds Docker images from it, and stands up the Lambdas, the Batch job for garbage collection, the queue and the Step Functions orchestration. The payoff is the last card: the deployment shape is identical across datasets. The only things that vary from project to project are the processor and the environment file.

Forward processing architecture

New files land, the store stays current

⚡Announced

New objects in the data bucket raise S3 notifications to SNS. Set SNS_TOPIC and the stack wires the subscription to its queue for you.

≡Buffered

The SQS queue absorbs bursts and sets the pace. SQS_BATCH_SIZE controls how many files one Lambda invocation handles — and therefore files per commit.

♻Maintained

Garbage collection runs on a Batch cluster on the schedule set by GARBAGE_COLLECTION_FREQUENCY, expiring old snapshots so the store doesn't grow without bound.

This is the steady-state path. New objects arriving in the source bucket raise S3 notifications onto an SNS topic; you point the SNS_TOPIC setting at it and the stack wires up the subscription itself. The queue is doing real work here — it absorbs bursts from upstream and it sets the rate at which you write. SQS_BATCH_SIZE controls how many file messages go to a single Lambda invocation, and since the consumer commits once per batch, that setting is effectively your files-per-commit ratio. And because Icechunk keeps history, garbage collection is not optional; it runs as a scheduled Batch job, expiring snapshots older than the configured frequency. Worth stressing that this is the boring, always-on half of the system, and it is the half people usually underestimate when they build this themselves.

Two paths

Load the archive once, then keep it current

⛏Backfill

A one-time, high-throughput bulk load of a large body of existing files. Initializes the store at full shape for every time step the inventory covers and uses a partitioned fork-and-merge cooperative distributed write, so many thousands of files process in parallel behind a small number of commits. Orchestrated by Step Functions.

▶Forward

The path for new production files as they become available. Files are announced to an SQS queue, consumed by a Lambda, written to the main branch and committed per batch. Not always an append: a coordinate already inside the store's extent is an in-place region="auto" write.

Sequencing them

  1. Deploy with BACKFILL_ENABLED=true; the forward consumer is held off automatically so backfill bootstraps main first.
  2. Configure SNS_TOPIC now — newly published files buffer in the queue while the backfill runs.
  3. Backfill completes and promotes. Set FORWARD_QUEUE_ENABLED=true, redeploy, and the queue drains onto the loaded store.
  4. Anything published between building the inventory and the subscription going live can be replayed onto the queue by hand — no data gaps.
Two complementary paths, and a typical project uses both. Backfill is the one-time bulk load of the existing archive; it declares the store at its full shape up front and uses a partitioned fork-and-merge write so thousands of files can land behind a handful of commits. It is off by default because plenty of projects only need the forward path. Forward processing handles new files as they arrive, committing once per queue batch. One subtlety worth calling out: after a backfill the store already holds a row for every coordinate in its extent, so a forward write is frequently not an append — writing it as one would duplicate the file and leave the axis non-monotonic. Those have to be in-place region writes. The sequencing matters and it is the part people get wrong. Deploy with backfill enabled and the forward consumer is held off automatically. Configure the SNS topic immediately anyway, so files published during the backfill accumulate in the queue rather than being lost. When the backfill promotes, flip the forward queue on and redeploy, and the queue drains onto a fully loaded store. Finally, there is a small window between when you built the inventory and when the subscription went live — those files can simply be pushed onto the queue manually.

Backfill · the problem

Why you can't just append the archive

✕Appending to main

A thousand workers all move the same branch tip, and you get one commit per file — maximum contention, worst writes-per-commit ratio.

✓Fork and merge

Declare full shape on a backfill branch. Workers fork a clean snapshot, write disjoint regions, never commit. A reducer merges into one commit.

Region disjointness is the operator’s responsibility — two workers writing the same region will fail to merge.

This is the mechanism that makes bulk loading tractable. The naive approach is to run the forward path very wide: point thousands of workers at the archive and let them append. That fails on contention — every worker is trying to move the same branch tip — and even if it did not, you would be making one commit per file, which is the worst possible writes-per-commit ratio and leaves you a history to garbage collect afterwards. Fork and merge inverts it. You declare the store at its full final shape up front, on a dedicated backfill branch so the load stages to the side and main is untouched until the end. Each worker forks a clean committed snapshot, writes its files into a disjoint region of the array, and does not commit. A reducer merges all those forks into a single commit. Because only the reducer commits, there is no contention at all. The one thing to be honest about is the caption: disjointness is yours to guarantee. Two workers writing the same region will not merge, and the pipeline cannot check that for you.

Backfill · the mechanics

Init → Fork → Workers → Reduce → Promote

  1. Init. The coordinator creates the store with the dataset's full dimension extent for the inventory, on a backfill branch, and commits. Workers can only fork a clean snapshot.
  2. Partition. The inventory is split into partitions. Each becomes one commit, and partitions run serially.
  3. Fork. The coordinator forks the committed base snapshot for this partition.
  4. Workers. A distributed Map fans batches of keys to Lambdas. Each copies the fork, writes its files via vds.vz.to_icechunk(fork.store, region="auto"), and pickles its fork to S3. No commits.
  5. Reduce. When the partition's workers finish, a reducer merges every pickled fork into a single commit. Then the next partition forks from that new tip.
  6. Promote. After the last partition, main is fast-forwarded to the backfill tip.
SettingDefaultWhat it trades
BACKFILL_PARTITION_SIZE500Files per partition = files per commit. Larger means fewer commits, but a failure loses more work.
BACKFILL_MAX_ITEMS_PER_BATCH10Files per worker, i.e. per child fork. Bounded by the Lambda timeout.
BACKFILL_MAX_CONCURRENCY50Workers in flight per partition. Cap it to respect rate-limited upstreams such as NASA EDL.
The concrete sequence, orchestrated as an outer serial Map over partitions, each running Fork, then an inner Distributed Map of parallel worker Lambdas, then Reduce, with a final Promote. Init creates the arrays at their full final shape with coordinates written as metadata, on a backfill branch, and commits — it has to leave nothing pending, because a fork can only be merged if its base is a clean committed snapshot. Partitioning decides your commit granularity. Workers copy the fork, write with region equals auto, and pickle the fork to S3 rather than committing. The reducer merges the partition's forks into one commit, and the next partition forks from that new tip — which is why partitions are serial. Finally main is fast-forwarded to the backfill tip, and only at that moment does the loaded data become visible on main. The table is where the operational judgment lives. Partition size is a bet: bigger partitions mean fewer commits but more lost work when a partition fails, because none of its files commit. Items per batch is bounded by the Lambda timeout. And concurrency is where you protect a rate-limited upstream from yourself — if you are pulling through something like NASA Earthdata Login, this is the setting that keeps you from being throttled.

Where this is actually running. Five deployments, and deliberately not five variations on the same dataset. HRRR is a high-resolution numerical weather model on hourly cycles. TEMPO is a geostationary air-quality spectrometer scanning North America hourly during daylight. NAQFC is operational air-quality forecast guidance. GOES CF is geostationary observational imagery. And GPM IMERG is half-hourly global precipitation. Different agencies, different source formats, very different cadences and volumes — an hourly forecast cycle behaves nothing like a half-hourly observational archive. The thing worth drawing out is the last card: what these share is not the data, it is everything underneath the processor. Each one implements its own parsing and concatenation logic, and then deploys the identical stack. That is the whole argument of the talk, demonstrated rather than asserted. Adoption

What it takes to stand one up

  1. Create your repo from the template.
  2. Write processor.py against the protocol, replacing the sample.
  3. Add tests — in-memory Icechunk fixtures ship with the template.
  4. Configure .env: buckets, region, SNS topic, batch sizes.
  5. Review with cdk synth, then cdk deploy.
  6. Backfill: upload an inventory, run start_backfill.sh.
  7. Enable forward processing and redeploy.

▶Forward methods

initialize_repo · initialize_session · process_file · commit_processed_files

⛏Backfill methods

initialize_backfill_store · open_backfill_repo · process_backfill_file

♻Shared

garbage_collect — used by both paths, run on the configured schedule.

That's the surface. Eight methods and an .env file. Everything else on the previous slides is already written and tested.
This is the honest accounting of what adoption costs. Seven steps on the left, and the right-hand column is the entire API surface you implement. Four methods drive forward processing: open the repository, open a writable session, process a file, commit. Three more are backfill-specific: initialize the backfill store at full shape, open the repo, and write a single file into a worker's fork without committing. Garbage collect is shared. That is it — eight methods and an environment file, and only five of them if you skip backfill. Worth pausing on step three: the template ships in-memory Icechunk fixtures and sample tests, so you can develop and test your processor without deploying anything to AWS. That is usually where most of the work actually happens, and it is a fast loop. Everything on the architecture and backfill slides — the orchestration, the fork and merge, the queue wiring, the garbage collection — is already written and under test.
